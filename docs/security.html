Security

Each repository has its own SECURITY.md. This page summarizes practices that apply across the toolkit.

Reporting a vulnerability

Please report security issues privately to [CONTACT EMAIL]. Do not open a public issue for a vulnerability, and do not attach production evidence, alerts, secrets, or personally identifiable information.

This is community open-source software. There is no published service-level agreement for response times. Describe the issue, the affected path, and a safe way to reproduce it with synthetic data.

What the tools will not do

  • They will not target systems you do not own.
  • They will not mutate a host unless both CONFIRM=yes (or eu_monitor_confirm=yes) and a completed ROE with Status: AUTHORIZED are present.
  • They will not download vendor packages, import GPG keys, or pipe installers to a shell. Vendor fingerprints are not shipped in these repositories; copy them from current official vendor documentation.
  • They will not treat local baseline checksums as authentic against an attacker who already controls the operator account. Store baselines off-host or on immutable media if you need that assurance.

Residual risks to keep in view

  • Redaction is best-effort. Review every report before sharing it.
  • Parsing of ss, last, and auth logs varies by operating system. Counts of zero are data, not proof that a tool had a complete view.
  • The Wazuh rules are untested against a live manager. Parent SIDs can change between Wazuh versions. Untuned “unusual hours” and “multiple failures” rules will produce noise or miss events.
  • Same-user tampering of reports and checksums is possible. Path guards refuse symlinks and foreign ownership, but they cannot stop an attacker who already is the operator account.
